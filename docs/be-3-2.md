# BE-3.2 · Generación del calendario de ida

`POST /api/v1/temporadas/{id}/calendario/generar`, solo ORGANIZADOR.

```json
{
  "fechaPrimeraJornada": "2028-02-12",
  "horaPrimerTurno": "08:00",
  "canchaIds": [1, 2],
  "arbitroIds": [
    "00000000-0000-4000-8000-000000000012",
    "00000000-0000-4000-8000-000000000013"
  ]
}
```

La fecha debe ser posterior al día actual de El Salvador; no se admite hoy aunque la hora aún sea futura. Las horas usan America/El_Salvador (UTC-06). Las listas no admiten duplicados; los árbitros son UUID, no números. Omitir `arbitroIds` selecciona todos los ARBITRO activos ordenados por id; enviarlo vacío es un error. Cuando se indican listas se conserva su orden para asignación.

Con 12 equipos, respuesta 201:

```json
{
  "temporadaId": 1,
  "jornadas": 11,
  "partidos": 66,
  "estadoJornadas": "BORRADOR"
}
```

## Decisiones confirmadas con Carlos

- Se exige que el número de INSCRITO sea exactamente `temporada.maxEquipos`. El generador admite cualquier cupo: con N par crea N-1 jornadas; con N impar crea N jornadas y cada equipo descansa una vez. En ambos casos crea N*(N-1)/2 partidos. Los descansos no son partidos ni equipos ficticios en la base.
- Cualquier partido no CANCELADO bloquea la generación con 409, incluidos EN_CURSO y FINALIZADO. Si todos están CANCELADO, se permite regenerar y se conservan todas sus filas.
- Se reutilizan las jornadas BORRADOR existentes por número, conservando sus ids. Si existe alguna PUBLICADA se rechaza con 409. Las jornadas BORRADOR fuera del rango generado se conservan sin modificarlas; la respuesta cuenta las jornadas del nuevo plan.

## Algoritmo y transacción

Equipos ordenados por id, círculo con el primero fijo, alternancia de local según índice de pareja + ronda. Se omite el emparejamiento de descanso. Las rondas se separan siete días, de modo que cada equipo juega como máximo una vez por semana.

Los partidos se asignan en orden cronológico, por turno de 90 minutos y cancha. Los árbitros rotan globalmente con k % cantidad y la diferencia de carga máxima es uno. Se requieren al menos tantos árbitros como canchas efectivamente simultáneas, `min(canchas, floor(N/2))`. Todos deben estar activos. El último turno puede terminar exactamente a medianoche local; no puede superarla.

Se usa una transacción ReadCommitted con bloqueo FOR UPDATE sobre la temporada, compatible con los bloqueos de H2 y BE-3.1. La comprobación de inscritos, calendario previo, jornadas, creación y los partidos quedan dentro de la misma transacción. Una segunda generación concurrente espera y después responde 409. La transacción permite 15 segundos para insertar el calendario.

Las exclusiones de DB-3.1 siguen protegiendo cancha y árbitro frente a calendarios de otras temporadas. Los conflictos se traducen con el mismo manejador de BE-3.1. El generador no desplaza automáticamente los turnos solicitados para buscar otros libres. Cualquier error revierte el plan completo, sin borrar el historial o jornadas que ya existían.

## Errores

- 400: cuerpo inválido, listas vacías/duplicadas, fecha no futura, hora o UUID inválidos.
- 401/403: sesión o rol incorrectos.
- 404: temporada, cancha o árbitro inexistente.
- 409: partidos no cancelados, jornadas publicadas o conflicto SQL de recursos.
- 422: `{ inscritos, requeridos, faltan }` cuando el cupo no coincide; `{ arbitros, requeridos }` cuando no hay suficientes árbitros; cancha inactiva, árbitro inactivo/sin rol o turnos que no caben en el día.
